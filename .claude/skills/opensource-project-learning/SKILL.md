# 开源项目学习 Skill（对话式版本）

## 📚 **Skill 概述**

这个 skill 提供了一个**对话式**的方法来学习任何开源项目。核心原则是：**每一步只给1-2个要点，然后停下来等待用户反馈**。

## 🎯 **适用场景**

- 用户想要学习一个新的开源项目
- 用户想要理解某个项目的架构和设计
- 用户需要快速了解项目的核心功能
- 用户想要探索项目的代码实现
- 项目类型不限（Web应用、后端服务、CLI工具、插件等）

---

## 🔄 **核心原则**

**重要：这是一个对话式 skill，不是文档式教程！**

1. **少而精**：每次只提供1-2个要点，不要一次性输出大量信息
2. **逐步推进**：每一步都要停下来，等待用户反馈或问题
3. **初步主动，深入询问**：基本信息可以主动提供，但深入分析前必须询问
4. **不主动挖掘**：除非用户明确表示兴趣，否则不要深入技术细节
5. **建议式引导**：基于项目特点给推荐选项，而不是开放式问题

---

## ❌ vs ✅ 交互示例

**❌ 错误示例（文档式 - 不要这样做）：**
```
我: [读取10个文件] 这是一个完整的项目报告，包括技术栈、架构、功能...
[输出2000字长报告，包含所有细节]
```

**✅ 正确示例（对话式 - 应该这样做）：**
```
我: [读取README] 这个项目是 Claude Code 的状态栏插件。
它的核心功能是实时显示上下文使用情况。

这听起来对你有用吗？你想先了解：
1. 它具体显示哪些信息
2. 技术实现原理
3. 其他方面

[等待用户回答]
```

## 📖 **对话式学习流程**

### **阶段 0: 快速上手（实践优先）**

**目标**: 先让项目跑起来，通过使用理解价值，而不是先看文档

**核心原则**: **用→理解→深入**

```
[读取 README 的安装/快速开始部分]

我: 这个项目可以通过[简单步骤]快速上手。

步骤：
1. [安装命令]
2. [运行命令]

你想：
1. 直接运行看看效果
2. 先了解它能做什么
3. 其他

[等待用户回答]
```

**为什么先运行？**
- ✅ 通过实际使用理解价值，比看文档更直观
- ✅ 看到运行效果后，更有动力了解实现原理
- ✅ 从使用问题中反推设计理念和最佳实践
- ✅ 避免"看了半天不知道干什么"的问题

#### **步骤 1: 引导用户运行项目**

**优先级：最高**

```
用户: "我想先了解它能做什么"

我: 好的，但我建议先运行看看效果，这样更容易理解。

[给出安装和运行命令]

需要我帮你检查环境或运行吗？

[等待用户回答]
```

**如果用户选择运行**：
```
我: 让我们一步步来：

1. 先检查环境：[检查命令]
2. 安装依赖：[安装命令]
3. 运行项目：[运行命令]

每一步都要等成功后再继续。

准备好了吗？

[等待用户确认，然后一步步引导]
```

#### **步骤 2: 从使用体验中学习**

**运行成功后，通过对话引导思考**

```
我: 恭喜，项目跑起来了！🎉

刚才的运行过程中，你注意到什么了吗？

比如：
1. [观察1: 基于项目特点，比如"它实时显示了状态"]
2. [观察2: 基于项目特点，比如"配置很简单"]

想了解这些观察背后的实现原理吗？

[等待用户回答]
```

**关键点：**
- ✅ 从使用体验中提出观察
- ✅ 将观察与技术实现关联
- ✅ 让用户自己发现问题，然后解释

#### **步骤 3: 如果运行失败**

**不要直接放弃，而是引导调试**

```
我: 遇到错误了。让我们看看是什么问题。

[分析错误信息]

这个错误说明[解释原因]。

解决方法：
1. [方法1]
2. [方法2]

需要我帮你执行吗？

[等待用户回答]
```

### **阶段 1: 初步了解（在运行之后）**

**目标**: 在已经运行过项目的基础上，通过对话了解设计理念

**此时用户已经：**
- ✅ 看到了项目运行效果
- ✅ 有了直观的使用体验
- ✅ 可能遇到了一些问题

**这种情况下再阅读文档，效果更好**

#### **步骤 1: 从 README 开始（现在有了上下文）**

**只读 README，不要读其他文件**

```
[读取 README.md]

我: 这个项目是[一句话描述，不超过15字]。

它的核心作用是[一个关键功能，不超过20字]。

你想了解：
1. [基于项目特点的建议选项1]
2. [基于项目特点的建议选项2]
3. 其他你感兴趣的

[等待用户回答]
```

**为什么只读README？**
- README 通常包含项目的核心信息
- 避免信息过载
- 让用户引导学习方向

**响应策略：**
- **如果用户问技术细节** → 读取 package.json/Cargo.toml，**只回答用户问的**
- **如果用户问架构** → 询问想了解哪个模块，不要主动分析整个结构
- **如果用户说"继续"** → 给下一个要点，然后停

#### **步骤 2: 根据用户兴趣深入**

**只在用户明确询问时才深入**

```
用户: "它用了什么技术？"

我: [读取 package.json]

它主要用了[技术栈名称]。

有具体哪个技术你想深入了解吗？

[等待用户回答]
```

**关键点：**
- 不要列举所有依赖
- 不要主动解释每个技术的作用
- 只回答用户问的

---

### **阶段 2: 探索代码结构**

**目标**: 帮助用户理解项目组织，但不要一次性展示整个目录树

#### **步骤 1: 了解项目规模**

```
我: 项目大约有[X个文件，Y行代码]。

你想先了解：
1. [建议1: 基于项目特点，比如"入口点在哪里"]
2. [建议2: 基于项目特点，比如"主要模块有哪些"]
3. 其他

[等待用户回答]
```

#### **步骤 2: 深入具体模块**

**只在用户询问时才读取代码**

```
用户: "入口点在哪里？"

我: [读取 src/index.ts]

入口点做了这些事情：
1. [要点1]
2. [要点2]

你想深入了解哪个部分？

[等待用户回答]
```

**不要做的事情：**
- ❌ 不要主动读取10个文件然后给出总结
- ❌ 不要分析整个代码架构
- ❌ 不要给出完整的函数调用链

---

### **阶段 3: 运行项目（可选）**

**目标**: 帮助用户运行项目，但只在用户询问时提供

```
用户: "我能运行看看吗？"

我: 可以。根据 README，你需要：
1. [步骤1]
2. [步骤2]

需要我帮你检查环境吗？

[等待用户回答]
```

## 🎯 **从使用中学习最佳实践**

### **核心思想：用→理解→深入**

前期学习应该优先通过实际使用来理解项目价值，而不是先啃文档。

### **为什么先运行再看代码？**

| 传统方式（先看文档） | 实践优先（先运行） |
|-------------------|------------------|
| 看了半天不知道干什么 | 立即看到效果，有直观感受 |
| 不清楚为什么要这样设计 | 从使用中体验设计巧思 |
| 不知道重点在哪里 | 运行过程中自然产生疑问 |
| 容易放弃（太枯燥） | 有成就感，更有动力深入 |

### **对话式引导最佳实践**

#### **步骤 1: 运行前 → 激发兴趣**

```
我: 这个项目能解决[具体问题]。

比如，如果你遇到过[场景]，这个项目可以[解决方案]。

想试试看吗？

[等待用户回答]
```

#### **步骤 2: 运行中 → 观察和提问**

```
用户: [成功运行]

我: 太好了！🎉

你注意到什么了吗？
1. [观察点1: 基于实际输出]
2. [观察点2: 基于实际行为]

这些设计说明了[设计理念]。

[等待用户反馈]
```

#### **步骤 3: 运行后 → 总结最佳实践**

```
我: 刚才的使用过程中，我们发现了几个最佳实践：

1. **实践1**: [从使用中总结]
   - 为什么这样做：[理由]
   - 带来什么好处：[好处]

2. **实践2**: [从使用中总结]
   - 为什么这样做：[理由]
   - 带来什么好处：[好处]

想了解这些实践在代码中是如何实现的吗？

[等待用户回答]
```

### **典型对话流程示例**

**场景：学习 claude-hud 项目**

```
我: 这是一个 Claude Code 的状态栏插件。

它能解决的问题是：在使用 Claude Code 时，
你看不到上下文使用情况，可能突然就超限了。

这个插件会实时显示进度条，就像手机电池一样。

想试试看吗？

用户: 想

我: 好的，只需要3步：

1. 安装插件：/plugin install claude-hud
2. 配置状态栏：/claude-hud:setup
3. 重启 Claude Code

需要我帮你执行吗？

[用户安装并重启后]

我: 成功了！你现在应该能看到底部有状态栏了。

你注意到什么变化了吗？

用户: 多了两行，显示上下文百分比

我: 对！这就是它的核心价值。

现在你能在上下文达到 85% 之前就知道了，
而不是突然被截断。这给你更多时间调整策略。

想知道这个百分比是怎么计算出来的吗？

用户: 想

我: [才开始读取代码，解释实现原理]
```

### **从使用中发现的设计模式**

**在运行过程中，引导用户观察：**

1. **配置方式** → 理解项目的配置哲学
2. **错误处理** → 理解项目的健壮性设计
3. **输出格式** → 理解项目的用户体验考虑
4. **性能表现** → 理解项目的性能优化策略

**每次观察后，都停下来询问：**
```
你觉得为什么这样设计？

[等待用户思考，然后解释]
```

### **将使用体验与技术实现关联**

```
我: 你刚才看到的[现象]，在代码中是这样实现的：

[读取相关代码片段，1-2个要点]

关键点是：
1. [技术点1]
2. [技术点2]

这样就解释了你刚才看到的行为。

清楚了吗？

[等待用户反馈]
```

## 🎯 **引导式提问模板**

不要问开放式问题，要给建议性选项：

**❌ 不好的提问：**
```
"你想了解什么？"
"你想看哪部分？"
"你对什么感兴趣？"
```

**✅ 好的提问：**
```
"这个插件主要显示3类信息：上下文、工具活动、待办事项。
你想先了解哪一类？"

"这是个 TypeScript 项目。你想先了解：
1. 入口文件
2. 核心逻辑
3. 渲染系统"
```

---

## 📊 **信息粒度控制**

### **每次只给1-2个要点**

**示例：**

```
✅ 好的做法：
"它有2个核心功能：
1. 实时显示上下文使用情况
2. 追踪工具和代理活动

想了解第一个功能的实现原理吗？"

❌ 不好的做法：
"它有以下功能：1. 上下文监控 2. 工具追踪 3. 代理状态 4. 待办事项 5. Git集成 6. 使用限制..."
```

## 🚦 **何时停下来询问**

### **必须停下来的时候：**

1. **给完1-2个要点后** → 等待反馈
2. **准备读取新文件前** → 询问是否需要
3. **用户可能不熟悉某个技术时** → 询问是否需要解释
4. **准备深入分析前** → 确认用户兴趣

### **可以继续的时候：**

1. **用户明确说"继续"**
2. **用户说"多告诉我点"**
3. **用户问具体问题**

## 🛠️ **技术栈适配指南**

当用户询问某个技术时，参考这些简短解释：

### **JavaScript/TypeScript**
- **package.json**: 依赖和脚本配置
- **tsconfig.json**: TypeScript 编译配置
- **src/**: 源代码目录

### **Python**
- **requirements.txt**: 依赖列表
- **setup.py**: 项目配置
- **package_name/**: 主要代码

### **Go**
- **go.mod**: 依赖管理
- **cmd/**: 命令行入口
- **pkg/**: 库代码

### **Rust**
- **Cargo.toml**: 项目配置
- **src/**: 源代码

**只解释用户问的部分，不要主动展开。**

## ✅ **检查清单**

在应用此 skill 时，确保：

### **前期学习（阶段0）**
- ✅ **优先引导用户运行项目**，而不是先看文档
- ✅ 通过实际使用理解项目价值
- ✅ 从使用体验中总结最佳实践
- ✅ 将观察到的现象与技术实现关联

### **对话交互**
- ✅ 每次只给1-2个要点
- ✅ 每一步都停下来等待用户反馈
- ✅ 不主动深入技术细节
- ✅ 给建议性选项而不是开放式问题
- ✅ 只在用户询问时读取新文件
- ✅ 基于用户反馈调整信息粒度

### **学习路径**
```
阶段0: 快速上手 → 运行项目 → 使用体验
   ↓
阶段1: 初步了解 → README → 设计理念
   ↓
阶段2: 深入探索 → 代码实现 → 架构理解
```

**优先级：** 阶段0 > 阶段1 > 阶段2

## 💡 **注意事项**

1. **用户偏好** - 有些用户喜欢详细，有些喜欢简洁，根据反馈调整
2. **项目状态** - 已废弃的项目需要特别说明
3. **时间限制** - 根据用户可用时间调整深度
4. **语言障碍** - 非英文文档可以提供翻译
5. **安全性** - 不信任的项目建议在沙箱运行

---

## 🔄 **持续改进**

这个 skill 会根据实际使用情况不断优化。如果发现某个模式效果好，可以记录下来作为最佳实践。

**关键指标：**
- 用户是否持续参与对话
- 用户是否主动提问
- 用户是否表示"理解了"
- 用户是否要求更多细节

如果用户长时间不回复或表示"太复杂"，说明信息粒度可能需要调整。

通过这个对话式 skill，用户可以按照自己的节奏和兴趣方向学习开源项目，而不是被大量信息淹没。
